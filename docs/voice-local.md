# Голос Hub: локальный LiveKit

Голос работает через self-hosted LiveKit на этой Ubuntu. Платный Cloud, DNS,
публичный HTTPS, роутер, TURN и UDP-порты сейчас не настраиваются. Аудио идёт
через WebRTC (DTLS-SRTP), а не через Socket.IO. Это не E2EE: LiveKit — доверенный SFU.

## Запуск (Ubuntu, корень репозитория)

Node.js на хосте не нужен:

```bash
sudo docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/work" -w /work node:24.21.0-bookworm-slim node scripts/setup-voice.mjs
sudo docker compose --profile voice config --quiet
sudo docker compose build api web
sudo docker compose up -d --wait db
sudo docker compose run --rm migrate
sudo docker compose --profile voice up -d --wait livekit api web
```

Если `.env` ещё нет — сначала выполните первоначальную подготовку из README.
`setup-voice.mjs` добавляет случайные ключ/секрет только при их отсутствии,
меняет **только VOICE_ENABLED на true**, сохраняет остальные значения, права 0600.
Не печатает секреты. Повтор безопасен. Не редактируйте секрет вручную ради теста.
Если после аварии остался `.env.voice-tmp`, сначала проверьте причину; скрипт
откажется его перезаписывать. `.env*` не попадает в Git/образ frontend.

LiveKit: образ `livekit/livekit-server:v1.13.7`, профиль Compose `voice`, отдельный
процесс не от root, лимиты 1 GiB / 1.5 CPU, healthcheck, ограниченные логи,
restart unless-stopped. После изменения `infra/livekit.yaml` выполните
`sudo docker compose --profile voice restart livekit`: обновление bind-mounted
файла само по себе не перезапускает процесс. Конфигурация — `infra/livekit.yaml`, секреты — env только
LiveKit/API. Redis не требуется для одного SFU. API 7880, debug/metrics/TURN/UDP
не публикуются. Единственный новый host bind — **127.0.0.1:7881/TCP**.
20 мест в комнате — защитный лимит конфигурации, не измеренная ёмкость сервера.

## Туннель для Windows

Обычный HTTP-туннель 8080 переносит интерфейс и сигнализацию, **но не аудио**.
В отдельном CMD Windows запустите:

```cmd
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:8080:127.0.0.1:8080 -L 127.0.0.1:7881:127.0.0.1:7881 hub
```

Если окно с прежним **браузерным** туннелем 8080 ещё работает, завершите именно его
и замените приведённой командой, иначе порт занят. Существующий `hub-proxy` и
туннель доступа инструментов не трогайте. Другой вариант — оставить браузерный
туннель и открыть дополнительное соединение только с `-L 127.0.0.1:7881:127.0.0.1:7881`.

Проверка реализации и автоматических сценариев: [test-results.md](test-results.md).

Откройте **http://localhost:8080**. localhost считается безопасным контекстом
браузера для getUserMedia, хотя схема HTTP. Адрес `http://<UBUNTU_LAN_IP>:8080`
не является заменой: сервис там не опубликован, и обычный HTTP LAN-адрес
не обеспечивает доступ к микрофону.

LiveKit принудительно использует ICE/TCP и объявляет 127.0.0.1:7881. Для браузера
это loopback **Windows**, где SSH принимает соединение; затем переносит его к
loopback Ubuntu и далее в контейнер. 127.0.0.1 внутри API, LiveKit, Ubuntu и Windows
не считается одним узлом: связи заданы явно. Сигнализация идёт через Caddy →
backend-шлюз → LiveKit по `/livekit/rtc`; административные URL шлюз не пропускает.

## Ручная проверка

1. В настройках сообщества OWNER/ADMIN создаёт канал с типом «Голосовой».
2. Выбрать канал, нажать «Подключиться к голосу». Микрофон изначально выключен.
3. Нажать «Включить микрофон», разрешить браузеру устройство. При отказе Hub
   объяснит, где разрешить доступ; можно оставаться слушателем.
4. Второй аккаунт в другом профиле/браузере присоединяется по приглашению и
   входит в тот же голосовой канал. Лучше использовать наушники.
5. Убедиться, что видны реальные участники, слышен звук и загорается «Говорит».
6. Проверить выключение микрофона и воспроизведения. Если браузер запретил
   autoplay, нажать «Разрешить воспроизведение».
7. Переключить текстовый канал — голос остаётся. Перейти в другой голосовой —
   предыдущая комната покидается; то же правило действует между вкладками.
8. Проверить выход, logout, исключение вторым владельцем и удаление канала:
   доступ прекращается на SFU, а не только скрывается кнопка.
9. Кратковременно прервать сеть: показать reconnect и восстановить соединение.
   При полном закрытии комнаты/отзыве доступа повторный вход требует новой проверки.

Голос не подключается автоматически после обновления страницы: вход явный,
чтобы не включать микрофон без действия пользователя. Краткий сетевой разрыв
обрабатывает LiveKit SDK. При окончательной ошибке показывается повторное подключение.

## Проверка двух устройств без публичной сети

Публичный IP не обязателен для закрытого теста: **на каждом** компьютере с SSH-клиентом
нужны собственные loopback-перенаправления 8080 и 7881 к этой Ubuntu, браузер,
микрофон и наушники. Подключение SSH уже должно быть разрешено и настроено отдельно.
Оба устройства открывают свой localhost:8080. Эта схема не требует LAN-публикации
Hub или изменения роутера. Телефон без подходящего SSH port forwarding таким
способом проверить нельзя; потребуется отдельно согласованная защищённая сеть/HTTPS.

## Что этот режим не доказывает

Один `-L 8080` не позволяет полноценно проверить WebRTC media. Дополнительный
TCP-туннель позволяет реальное аудио, но не проверяет UDP, NAT, STUN, TURN fallback,
поведение мобильных сетей, пропускную способность домашнего uplink и задержки
публичного маршрута. TCP через SSH имеет head-of-line blocking и хуже переносит
потери, чем обычный UDP WebRTC. Это локальная проверка, не производственная сеть.
Автотест с синтетическим микрофоном проверяет реальные RTP-пакеты и участников;
он не проверяет физические микрофоны, акустику, эхоподавление и слышимость человеком.

## Диагностика

```bash
sudo docker compose --profile voice ps
sudo docker compose logs --tail=60 livekit api
```

Не публикуйте `.env`, JWT, query strings сигнализации и traces браузера.
`voice_reconcile_failed`/`voice_revoke_pending` означают, что LiveKit недоступен
для служебного API; отзыв повторяется каждые 2 секунды. Текстовый commit при этом
не отменяется. Новые/повторные signaling подключения всё равно проходят проверку
членства и сессии. При сетевом разделении API↔SFU немедленное принудительное
отключение уже текущего медиапотока невозможно гарантировать до восстановления
служебной связи. Нельзя раскрывать 7880 напрямую: это обойдёт шлюз отзыва токенов.

Для отключения голоса: установить `VOICE_ENABLED=false` в `.env`,
`sudo docker compose up -d api`, затем `sudo docker compose --profile voice stop livekit`.
Текст и данные сохраняются. Не выполнять `down -v`. Голосовые каналы останутся в БД.

## Будущие rtc.mrloic.ru и turn.mrloic.ru

Это отдельный этап: DNS в Beget, доверенные HTTPS/WSS сертификаты, публичный адрес
и корректные ICE candidates, выбранные UDP/TCP диапазоны и маршрутизация Hyper-V/NAT,
TURN/TLS и TURN/UDP с временными учётными данными, firewall, мониторинг, нагрузочные
и security-проверки. Нельзя просто направить rtc-домен на открытый LiveKit 7880:
необходимо сохранить backend-проверку сессии/lease для сигнализации и продумать
cookie/Origin между доменами. TURN секреты остаются серверными. UPnP не используется.
Камера и демонстрация экрана не входят в текущие токены/интерфейс.

Источники: [LiveKit deployment](https://docs.livekit.io/transport/self-hosting/deployment/),
[ports](https://docs.livekit.io/transport/self-hosting/ports-firewall/),
[tokens](https://docs.livekit.io/frontends/reference/tokens-grants/),
[server config](https://github.com/livekit/livekit/blob/master/config-sample.yaml).


Production теперь подготовлен отдельно: [public-deployment.md](public-deployment.md).
Локальная конфигурация этой инструкции остаётся TCP/SSH без TURN. В production
выбран TURN/TLS на 443 и UDP mux 7882; TURN/UDP не публикуется.
